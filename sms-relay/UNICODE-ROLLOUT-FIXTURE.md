# Disposable Unicode rollout experiment

`unicode-rollout.py` is an **app-only synthetic fixture tool, not a staging or production installer**. It refuses a root outside `$TMPDIR` or without `.unicode-rollout-disposable`; never remove those restrictions to deploy. It does not access cron, Twilio, or a remote host. It requires Python 3.9+, PHP CLI with PDO SQLite and sodium, a private root with `code/`, `config.json`, an existing database and a pre-created single-link `maintenance.lock`. Config/database must be direct children of root. `code/maintenance-lock.php` and `code/public/index.php` must already match this candidate: the tool cannot safely bootstrap an old or cached process. All participants must use that same lock inode. Run the integration fixture with:

```
python3 -m unittest discover -s tests -p test_unicode_rollout.py -v
```

The tests show the explicit arguments; `--file` names are relative to the source and already-existing code directory. The fixture refuses to replace the already verified `maintenance-lock.php` or `public/index.php` bootstrap through `--file`, even if the source supplies different files. The operator must explicitly provide the complete reviewed set of remaining files, installation and segment cap. Per-file rename is atomic, not the entire release; the gate covers the mixed-code interval. The PHP helper executes the candidate queue's additive `migrateSegmentSchema()` and `configureSegmentCap()`, not `install()`.

The private journal records generation identity, original send-flag presence/values, a hash of other configuration, and a hash of old tables and records; it does not include config secrets or old records. A marker plus exclusive flock fences cooperating API requests and workers; the exact authenticated STOP webhook bypasses it. In-flight shared holders must drain. SQLite writes serialize with STOP. The full legacy-table hash can change from a valid concurrent STOP or other writer; that makes verification fail closed and needs human analysis, not a claim of corruption. Atomic config replacement preserves unrelated JSON values and file mode, but not formatting, ownership, ACLs, extended attributes or concurrent edits. Such edits are outside this disposable test's assumptions.

On a normal success the original flags (including missing keys) are restored before the marker is removed. **On failure or hard interruption after the marker is installed, it is intentionally retained**, rather than reopening potentially mixed code or migrated data; flags may be false or, if interruption occurs during restoration, already restored. Rerun the identical command to recover forward; changed inputs/generation or old-record hashes fail closed. A hard kill before marker creation has made no config/database/code changes. An inherited lock keeps the migration subprocess fenced if its parent dies. Do not delete/replace the lock, marker or journal to force progress.

Limitations: the marker helps only a marker-aware bootstrap and cannot fence older processes, independent writers, already executing requests, or stale PHP-FPM/opcache. The CLI/loopback tests do **not** exercise real PHP-FPM/opcache invalidation, runtime identities, production filesystem semantics, backups or a deployment mechanism. Existing signed STOP can wait for a SQLite writer and may time out. No claim of delivery or staging readiness is made. An independently reviewed deployment-specific bootstrap, backup, actual runtime/opcache verification, permissions and recovery plan are prerequisites to a future separately authorized real rollout.
